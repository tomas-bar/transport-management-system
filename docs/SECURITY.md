# Security and deployment

The browser demo exercises all implemented modules using device-local IndexedDB and tab sessions. Its initial `admin / admin` and `owner / owner` accounts are test credentials, not server authentication. Client-side password hashing and company/role checks support testing only; they do not create trusted identity, company isolation or synchronization. Browser-local photos are not publicly hosted and are excluded from JSON exports. Existing browser records are never uploaded or replaced automatically. The separately built server application uses cookie authentication and company-scoped persistence.

## Decisions and sources

Reviewed on 2026-10-22:

- [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): use Node's stable scrypt implementation with N=131072, r=8, p=1, a random salt and 128 MiB work memory. Argon2id is preferred by OWASP; avoiding an experimental runtime primitive or another native cryptographic dependency makes scrypt a practical supported alternative. Passwords require at least 8 characters and accept Unicode, spaces and paste. Hashing concurrency and queue length are bounded.
- [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): 256-bit random session tokens, SHA-256 verifiers in SQLite, HttpOnly/SameSite=Strict cookies, Secure and __Host- prefix on HTTPS, 30-minute idle and 8-hour absolute expiry. Sessions are revoked at logout and password change. Authentication tokens never enter browser storage.
- [OWASP CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): all unsafe requests require the configured Origin; authenticated requests also require the session CSRF token. Login uses the same origin check and JSON-only input. SameSite is additional protection.
- [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): company scope comes from the server session, never a request's company ID. Driver responses contain assigned operations and permitted financial entries. Commands repeat authorization on the server. Owner administration exposes company membership metadata without credentials. Access to company operations requires an explicit, audited user preview. Preview is read-only by default; explicit acting mode enables operational actions under the effective user's permissions and preserves the real account and effective user in audit records. Company administrators cannot enter another company. Profile/password, credential changes and backup restore are blocked during preview/acting sessions.
- [OWASP file uploads](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html): authenticated private retrieval, bounded input and decoded dimensions, image decoding/re-encoding, generated IDs and removal of metadata. No original filename is used as a filesystem path. SVG and arbitrary document uploads are unsupported.
- [Node 24 SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html) and [crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html): parameterized queries, foreign keys, transactions and a stable built-in password derivation primitive.

## Storage

One Node process and one persistent SQLite database suit the initial small installation. Schema migrations use `user_version` and refuse databases from a newer server. Companies, accounts, sessions, audit records and private attachments have separate tables. Operational data and notifications remain one validated company snapshot with a revision, preserving the approved model and atomic commands. This is an intentional intermediate storage format, not fully normalized operational persistence. Schema normalization and multiple-server operation remain future work.

Company operations, generated events, revision changes, membership changes and their audit records commit together. Restore first retains the previous snapshot in `snapshot_backups`. Authentication secrets and session tokens are excluded from JSON workspace backups. Restores preserve registered identities and privileges, and never restore passwords.

The dedicated company reset route generates an empty or deterministic sample snapshot server-side, requires explicit confirmation and the current revision, and permits only the effective company administrator in a direct or explicit acting session. Read-only preview cannot reset data; arbitrary JSON restore remains blocked in acting mode. Clear permanently deletes that company's live operations, attachments, optional-module records and retained operational backups while preserving settings and registered accounts. Sample reset retains a preceding snapshot. Hosting-provider backups and audit metadata are outside this application-level clear action.

Photos are private JPEG derivatives stored in SQLite. Input is limited to 8 MiB and 20 million pixels, resized to at most 2400 pixels per side, with 20 photos per order and a 512 MiB live-image quota per company. Explicit deletion removes the live derivative; audit metadata remains. Photos stay until explicitly deleted. Snapshot JSON backups exclude image bytes; full SQLite backups contain photos. Operators must apply a retention policy and expire their database backups as appropriate. No end-to-end encryption, malware scanning service, or encryption at rest is claimed. Deployment should use encrypted persistent volumes and encrypted backups.

Draft and retrospective historical records are excluded from driver projections and operational commands. Both demo and server private photo routes repeat this visibility check against the current company snapshot, including requests for guessed order or attachment IDs. Publishing a draft repeats the normal resource, scheduling and load validation. Published work cannot be hidden by switching its mode; completed history protects existing route records and order links.

The browser policy allows HTTPS data connections because company administrators can configure map-provider endpoints. Application scripts remain same-origin; map requests send only the explicitly selected addresses and coordinates. Network egress settings remain independent of this browser policy.

## Hosting requirements

Serve the server-mode build and API at the same HTTPS origin through a reverse proxy. Set `KRYPTA_PUBLIC_ORIGIN` to that exact origin, bind Node to loopback behind the proxy, and provide a private persistent volume for `KRYPTA_DB_PATH`. Do not point the database at temporary or static-host storage. Configure TLS, service restart, backups, operating-system security updates and monitoring. The default listener does not trust forwarding headers for authentication or throttling; behind a proxy the shared source IP limits apply conservatively. Account limits remain separate. A deployment needing higher throughput should add a documented trusted-proxy configuration.

Sites can host the static browser demo or the separately built shared evaluation adapter described below. The latter runs on Cloudflare Workers with D1/R2 storage, independently of the Node process and its private SQLite file. Uploading the static demo does not start a shared backend. The existing Sites audience is a separate hosting setting and must be preserved unless the owner explicitly changes it.

Before real customer use, perform an independent security review, verify the production proxy/cookie behavior, test backup restoration and company migration, and configure operational monitoring. Email verification/recovery, MFA, billing, GPS and external freight integrations are not implemented.

## Shared Sites evaluation adapter

The `edge/worker.ts` adapter provides D1/R2-backed testing with server-owned identity and module/command checks. It uses its own HttpOnly cookie sessions, persisted rate limits, origin/CSRF checks and one-time account setup, so it can support the explicitly requested anonymous login page without exposing operational API data. Initial weak browser-demo passwords are replaced before use. See README for the adapter-specific PBKDF2, snapshot-size, backup and retention limits. JPEG uploads are client-decoded/re-encoded, then independently checked for bounded JPEG structure/dimensions and stripped of metadata on the Worker. This is less comprehensive than the Node sharp decoder and requires further review before real customer photos. The Node server and its documented password/session implementation remain separate.
